Security¶

Reporting a vulnerability¶

Report any vulnerability through a private vulnerability report on GitHub: https://github.com/kartnico/patrimeter/security/advisories/new.

  • Response within 7 days: acknowledgement, then assessment of the severity.
  • Fix published in a new version as soon as possible, within 90 days at the latest for a confirmed vulnerability; the CHANGELOG and the Release mention it.
  • Coordinated disclosure: please do not publish any detail before the fix; the person who reported the vulnerability is credited if they wish.

Only the latest published version receives security fixes.

Current state¶

Patrimeter is multi-user: separated accounts, mandatory password and TOTP second factor, wealth data encrypted with a key per user (docs/encryption.en.md), passkeys and FIDO2 keys. Authentication flows: docs/auth-flows.md (in French). Backups: docs/backup.en.md.

What is protected¶

  • Each user's wealth data: accounts, amounts, history, invisible and inaccessible to the other users.
  • Access to the accounts: password, second factor, sessions.
  • The confidentiality of registrations: the application does not reveal whether an address has an account.

Assumptions¶

  • The server administrator is trusted (see the limits below).
  • HTTPS is mandatory in production, on the server or on a reverse proxy declared in TRUSTED_PROXIES: passkeys and the __Host- cookie do not exist without it.
  • Dependencies come from recognised sources (Surý repository, Packagist, versioned composer.lock).

Sign-in log¶

Each user sees, on their My account page, their last 30 events (kept for 180 days): sign-ins, wrong passwords and codes, backup codes used, identity confirmations, changes of password, app or codes, closing the other sessions. Only the type, the success, the IP address, the browser and the date are recorded, never a secret.

Known limits¶

  • Active administrator: encryption protects against passive access (database, backups, sessions, logs). An administrator who changes the code can capture a password at the next sign-in; no web application escapes this.
  • Metadata visible to the administrator: email addresses, number of accounts, statements and ownership shares, months entered, number of budget categories and items and the months in which its amounts were saved, number of members of a family account, number of savings goals, order of the budget's categories and items, day of the monthly reminder chosen, whether a Carbure link exists, technical dates, sign-in log, open sessions (IP address, browser, dates) and trusted browsers. The app:user:list command shows part of it (addresses, dates, number of accounts, last sign-in), without decrypting anything.
  • Carbure: the instance address comes from the user. Patrimeter only calls …/api/mcp, with POST, without redirects, with a bounded delay and size, never sends back the response, and limits calls per user; CARBURE_ALLOWED_HOSTS restricts the hosts on an instance open to the public.
  • Password lost without a recovery key: the data is permanently lost.
  • Demo mode: off by default; turned on (DEMO_MODE=true), it lets anyone who reaches the sign-in page create a temporary account. Only turn it on for an instance dedicated to the demo (settings).
  • Leaked passwords: the check queries the Have I Been Pwned API (only the first 5 characters of the SHA-1 hash). Server without outbound access or service unreachable: it is skipped, and only the entropy is checked.
  • Without HTTPS, the password, the code and the session cookie travel in clear on the network. Behind a reverse proxy, the last hop to the server remains HTTP: keep it to a trusted network, and restrict it to the proxy's address (allow in the virtual host).
  • API token: whoever holds it reads the data in clear until it expires or is revoked. An MCP client sends what it reads to its provider.
  • Experimental libraries: symfony/mcp-bundle and mcp/sdk do not guarantee compatibility between versions yet; the MCP service is checked in the CI at every update.
  • Email alerts: the message of a critical error goes to ADMIN_EMAIL. It contains no secret or wealth data (filtered logs, encrypted data), but may mention an IP address or a path.
  • Restoring a backup: passwords, TOTP and recovery keys go back to their state at the time, and what was deleted since reappears (docs/backup.en.md).
  • Limiting by IP address: behind a reverse proxy, TRUSTED_PROXIES and X-Forwarded-For are essential, otherwise all attempts seem to come from the proxy and share the same counter.
  • Global block: 100 failures in one hour, all addresses together, block all sign-ins until the oldest ones leave this sliding hour; this is deliberate (distributed attack), at the cost of a possible denial of service.
